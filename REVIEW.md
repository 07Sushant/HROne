# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` | Returns `{"status": "ok"}` without pinging MongoDB. The spec says return 503 if the DB doesn't answer. | Start the app with a bad MONGO_URI — GET /health returns 200 instead of 503. | Added `db.command("ping")` inside a try/except; raises HTTP 503 on failure. |
| 2 | `create_employee` | `find_one` then `insert_one` is a check-then-insert: two concurrent requests both pass the check and both write, producing duplicate `emp_code` documents. | Fire two simultaneous POST /employees requests with the same `emp_code`; both return 201 but two documents exist. | Removed the `find_one` check. Now relies on the unique index on `emp_code` and catches `DuplicateKeyError` → 409. |
| 3 | `create_employee` | `datetime.now()` returns a naive datetime (no timezone). PyMongo stores naive datetimes as UTC, but returning them later without timezone context causes off-by-IST-offset bugs on read. | Inspect the stored document — `created_at` has no `tzinfo`. | Changed to `datetime.now(timezone.utc)` (UTC-aware). |
| 4 | `create_employee` | `created_at` is a Python `datetime` object in the returned dict. FastAPI serialises it to an ISO-8601 string, but the contract requires epoch **milliseconds** (integer). | POST /employees response — `created_at` is a string like `"2026-07-06T04:30:00"` instead of `1783025400000`. | `serialize_employee()` converts `datetime → int(dt.timestamp()) * 1000`. |
| 5 | `list_employees` — skip | `skip = page * page_size`. For page 1 this skips the first `page_size` records entirely. Page 1 should skip 0 rows. | GET /employees?page=1 returns the second page of results. | Changed to `skip = (page - 1) * page_size`. |
| 6 | `list_employees` — total | `total = db.employees.count_documents({})` — ignores the `department` filter. Filtering by department returns a `total` that is the whole collection size. | GET /employees?department=Engineering — `total` reports all employees, not just Engineering. | Changed to `db.employees.count_documents(q)` so `total` reflects the applied filter. |
| 7 | `punch_in` — missing 404 | `emp = db.employees.find_one(...)` is called but `emp` is never checked for `None`. An unknown `emp_code` raises a `TypeError` on `emp["shift_start"]` instead of a clean 404. | POST /attendance/punch-in with a non-existent `emp_code` — server crashes with 500 instead of 404. | Added `if not emp: raise HTTPException(404, ...)` immediately after the lookup. |
| 8 | `punch_in` — naive timestamp | `datetime.fromtimestamp(body.punched_at / 1000)` creates a naive datetime using the local system timezone, not UTC. On a server in a different timezone the stored time is wrong. | Run the server in UTC+8; punch in at a specific epoch ms — stored `punch_in` is off by 8 hours. | Changed to `datetime.fromtimestamp(ms // 1000, tz=timezone.utc)` (UTC-aware, whole seconds per R1). |
| 9 | `punch_in` — naive `datetime.now()` | The fallback `datetime.now()` is local time and naive. | Same timezone mismatch as #8 but on the fallback path. | Changed to `datetime.now(timezone.utc).replace(microsecond=0)` via the `now_utc()` helper. |
| 10 | `punch_in` — wrong IST date | `ts.date().isoformat()` extracts the **UTC** date from the timestamp. Near midnight IST (18:30–23:59 UTC = next IST day) the attendance date is one day behind. | Punch in at 18:40 UTC (00:10 IST the next day) — `date` is recorded as the UTC day, not the IST day. | Replaced with `get_attendance_date(ts, shift_start, shift_end)` which converts to IST first and handles overnight shift date attribution (R1). |
| 11 | `punch_in` — race condition | `find_one` check then `insert_one` — same problem as #2 but for attendance. Two simultaneous punch-ins for the same employee/date can both succeed. | Fire two parallel POST /attendance/punch-in for the same employee — two documents are created for the same day. | Removed the `find_one` guard. The unique compound index on `(emp_code, date)` makes the `insert_one` atomic; `DuplicateKeyError` → 409. |
| 12 | `punch_in` — `_id` / `id` leak | `doc["id"] = str(res.inserted_id)` adds a spurious `"id"` field that is not in the contract. `_id` (added in-place by `insert_one`) is also present until `pop`. | POST /attendance/punch-in response contains `"id": "..."` which is not in the `AttendanceRecord` schema. | Removed the `doc["id"] = ...` assignment. `serialize_record()` pops `_id` and returns only the contract fields. |
| 13 | `compute_late_minutes` — wrong timezone | `start = punch_in.replace(hour=h, minute=m, ...)` replaces the hour/minute on the **UTC** datetime. Shift times are IST, so comparing IST shift start against UTC punch time is wrong by 5h 30m. | An employee with a 09:30 IST shift who punches in at 04:00 UTC (09:30 IST exactly) gets computed as 0 late. But with the old code `start` = 04:30 UTC, making them appear 30 minutes early — so `late_minutes` could be negative (returned as 0 by `max`, hiding the bug). | Converted `punch_in` to IST first: `punch_ist = punch_in_utc.astimezone(IST)`, then built `shift_start_ist` on that IST datetime. |
| 14 | `compute_late_minutes` — wrong grace check | `minutes = int(elapsed_seconds / 60); return minutes if minutes > 10 else 0`. For elapsed = 601 s: `int(601/60) = 10`, and `10 > 10` is False → returns 0. But R2 says 09:40:01 (601 s late) → 10 late_minutes. | POST punch-in at 09:40:01 for a 09:30 shift — `late_minutes` = 0 instead of 10. | Changed the condition to `if elapsed <= 600: return 0` (check seconds directly, not the floored minutes). |
| 15 | `compute_work_hours` — banker's rounding | `round(x, 2)` uses Python's default "round half to even" (banker's rounding). R4 requires half-up. For work_hours = 8.125, `round(8.125, 2) = 8.12` (banker's) but the correct value is 8.13 (half-up). | Compute work_hours for exactly 8.125 hours — returns 8.12 instead of 8.13. | Replaced with `Decimal(str(value)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 16 | `compute_overtime` — missing 30-min threshold | Returns `max(0, int(elapsed_minutes))` with no check for the 30-minute minimum. R3 says overtime is 0 unless the excess is ≥ 30 minutes. | Punch out 15 minutes after shift_end — `overtime_minutes` = 15 instead of 0. | Added `if elapsed < 1800: return 0` before the floor computation. |
| 17 | `compute_overtime` — overnight shift date | `end = datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)` places shift_end on the attendance date. For an overnight shift (e.g. 22:00–06:00, `date` = July 6), shift_end is 06:00 IST on July **7** — not July 6. The old code compares against July 6 06:00 IST, making any punch-out that night appear to have ~16 hours of overtime. | Overnight-shift employee punches out at 06:40 IST — overtime should be 40 min, but old code returns ~1016 min. | Detect overnight (`eh*60+em <= sh*60+sm`) and add `timedelta(days=1)` to shift_end_ist. |
| 18 | `list_attendance` — full collection load | `list(db.attendance_logs.find(q))` loads **all** matching documents into Python memory, then sorts and slices them in Python. On 100 k records this loads the whole collection on every request. | Run against a large collection — response is slow and memory usage spikes. | Replaced with a cursor `.sort().skip().limit()` — MongoDB sorts and paginates in-engine. |
| 19 | `list_attendance` — wrong `total` | `total = len(docs)` counts only the in-memory slice after the Python sort. Once I moved to server-side pagination this would always equal `page_size`. | GET /attendance?page=2 — `total` returns `page_size`, not the real count. | Changed to `db.attendance_logs.count_documents(q)` before pagination. |
| 20 | `list_attendance` — `_id` / `id` leak | `d["id"] = str(d.pop("_id"))` exposes `"id"` in every attendance record response. | GET /attendance — each record contains `"id"` which is not in the `AttendanceRecord` schema. | Removed that line. Projection `{"_id": 0}` on the cursor excludes `_id`; `serialize_record()` handles datetime conversion. |
| 21 | `list_attendance` — no `date_from > date_to` validation | If `date_from > date_to` is sent, the query simply returns 0 results without error. The spec says this is a 422. | GET /attendance?date_from=2026-08-01&date_to=2026-07-01 — returns `{"items": [], "total": 0}` instead of 422. | Added `if date_from and date_to and date_from > date_to: raise HTTPException(422, ...)`. |

## Not a defect

- `body.model_dump()` in `create_employee`: correct for Pydantic v2; `dict()` is the v1 alias, both work.
- String comparison for YYYY-MM-DD dates (`"$gte": date_from`): lexicographic order is identical to chronological order for this format, so MongoDB string comparison on the `date` field is correct.
